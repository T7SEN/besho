## Why This File Exists

Training data for current LLMs predates several intentional removals from this codebase. Common autocompletion failures:

- Importing `web-push` because the agent saw a notification helper and pattern-matched on Web Push tutorials.
- Writing `import { Serwist } from '@serwist/next'` because the agent inferred PWA support from the Capacitor presence.
- Referencing `process.env.VAPID_PUBLIC_KEY` because the agent assumed Web Push must be configured.
- Reading from `pages/api/...` because the agent's training cutoff predates App Router maturity.
- Re-suggesting voice notes for `/permissions` because audio attachments seem like a natural fit for emotional context. They were prototyped and removed — don't re-propose without explicit user instruction.

Every entry above produces a runtime failure, a bundle that won't compile, or a refused PR. Stop the moment you find yourself typing one.

- **`currentWeekKey` in `@/lib/obedience` is NOT the same as `currentReviewWeekDate` from `@/lib/review-utils`.** They take the same `now: number` and return a `YYYY-MM-DD` Sunday string, but the semantics differ: `currentReviewWeekDate` returns the Sunday of the most-recently-completed reflection week (correct for `/review` — on Thursday you reflect on last week), while `currentWeekKey` returns the Sunday of the week CONTAINING `now` (correct for `/rewards` — events bucket into this week, not last week). The `obedience:bucket-shift-migration:done` sentinel + the Sir-only `migrateObedienceBucketShift` action shifted historical buckets forward by 7 days at fix time. Don't reintroduce the delegation; the helpers serve different features. Don't run the migration twice (sentinel-gated; second invocation is a no-op).
- **The "Cooldowns" tab inside `/admin/health` is the curated cooldown viewer via `getCooldownState()`.** SCANs `permission:reask-block:*` (capped at 200 keys), reads `safeword:cooldown:T7SEN` + `:Besho` TTLs, and SCARDs `permissions:denied-hashes`. Returns `ReaskBlockEntry[]`, `SafewordCooldownEntry[]`, and `deniedHashesCount`. UI ticks once per second locally subtracting elapsed seconds from the snapshot's TTLs — no Redis re-poll needed for the countdown animation. Don't propose mutating actions on this tab; it's strictly diagnostic. Use `/admin/redis` for arbitrary key probing — the Cooldowns tab is pre-curated for the common debug cases. Used to live at standalone `/admin/cooldowns` — that route was deleted when the diagnostics consolidation landed.
- **The safeword cooldown is per-author** (`safeword:cooldown:T7SEN` + `safeword:cooldown:Besho`) — NOT a single global key. Some old shorthand mentions just `safeword:cooldown` — that's stale; the actual keys are author-suffixed. 5-minute TTL, set by the safeword action.
- **`redis.scan(cursor, { match, count })` is the right API** for surfacing pattern-matched keys; Upstash supports it. Cursor `0` means "start"; the response's cursor `0` (or `"0"`) means "exhausted". The `getCooldownState` action uses a `safety` counter capping the loop at 50 iterations to bound cost defensively. Don't propose `KEYS pattern` — Upstash blocks long-running KEYS calls in the REST API; SCAN is the only safe way to enumerate by pattern.
- **`'use server'` files can only export async functions — Turbopack enforces this at build time, tsc does NOT.** A `tsc --noEmit` pass returning 0 does not prove a `'use server'` file is buildable. If you add `export const FOO = "bar"` or `export interface FooResult` to a `'use server'` file, tsc accepts it (interfaces compile away; consts are valid TS) but `next build` will fail with `"Only async functions are allowed to be exported in a 'use server' file."` and a single offending line cascades into 100+ "module has no exports" errors at every importer. **Interfaces and types DO compile clean** because they erase to nothing — the rule's actual bite is on `export const` / `export let` / `export var` / `export class` / `export function` (non-async). Move value exports to a sibling non-server module (e.g. `*-constants.ts`). Keep this in mind when running pre-flight checks: `pnpm build` is the gold standard, not `pnpm exec tsc --noEmit`.
- **Sentry filtering uses `ignoreErrors` (message-based), NOT `beforeSend` with stack-frame checks.** `beforeSend` runs in the browser BEFORE Sentry's source-map resolution, so frames you see in the Sentry UI (`fetchServerAction`, `server-action-reducer.ts`) do NOT exist in `beforeSend` — production frames are minified Turbopack chunks (function names like `r`, filenames like `/_next/static/chunks/abc-d8f3.js`). A stack-frame check that requires the literal string `fetchServerAction` works in dev, fails silently in prod. The fix lives in [`src/instrumentation-client.ts`](src/instrumentation-client.ts) — `ignoreErrors` matches against `event.exception.values[*].value` (the message string), invariant under minification. Currently filters: `/^Failed to fetch$/i`, `/^network error$/i`, `/^Load failed$/i`, `/^NetworkError when attempting to fetch resource\.?$/i`, and `"An unexpected response was received from the server."` Don't reintroduce a `beforeSend`-with-stack-frame approach; if a new message variant appears, add it to the regex list.
- **DeviceTracker heartbeat must `.catch()` — `void` does NOT catch.** The `void pingDevice(...)` operator just discards the return value; rejections still surface as unhandled promise rejections. Server actions POST to the current page URL, and on a 404 page (typo'd URL, deleted route) that POST returns the HTML 404 → Next throws `An unexpected response was received from the server.`. The heartbeat is best-effort by design (next 60s tick self-heals), so the call site is `pingDevice(...).catch(() => {})` not `void pingDevice(...)`. Don't revert this — it's the proximate fix for the unhandled-rejection issue captured by Sentry's onunhandledrejection mechanism.
- **`logger.error(msg, err)` calls `Sentry.captureException` — `logger.warn` does NOT.** This is the lever for "this catch block fired but isn't a code bug" cases. The FCM provider's catch around `POST /api/push/subscribe-fcm` classifies: `TypeError` matching the network-message regex → `logger.warn` (lands in activity feed only); anything else → `logger.error` (creates a Sentry issue). Same pattern applies to any best-effort fetch failure: log warn for network, error for genuine surprises.
- **`createPermission` is NOT idempotent — every call mints a fresh id, no body-hash dedup at the create layer.** A retry after `TypeError: Failed to fetch` could create two permission rows for one user intent (the request landed but the response was lost). The `createPermissionWithNetworkGuard` wrapper in `src/app/permissions/page.tsx` catches the network-error family and converts to `{ error: "Couldn't reach server. Check your connection and try again — your request may not have been sent." }` — explicitly NOT auto-retrying. Don't add auto-retry around this action; tell kitten to verify and re-submit.
- **`<StaffToolbar />` (Vercel production toolbar) is gated on `currentAuthor === "T7SEN"` AND `!isNative()`.** Per Vercel's docs, mounting `<VercelToolbar />` unconditionally prompts every visitor to log in to Vercel — that's why the gate exists. Both gates must pass: Sir-only on web. Capacitor APK skips the toolbar (no Vercel session in WebView). The component lives in [`src/components/staff-toolbar.tsx`](src/components/staff-toolbar.tsx), wrapped in `<Suspense fallback={null}>` in `src/app/layout.tsx`. Don't drop the suspense wrapper (Vercel docs require it for the App Router pattern). Don't expand the gate to Besho (would log her out of her account at the Vercel auth prompt).
- **Week-key picker uses snap-to-Sunday, not free-text.** The `EventLogViewer` in `/admin/rewards` had a free-text `<input type="text">` for `YYYY-MM-DD` that re-fetched on every keystroke (partial strings like "2026-04" would error mid-typing) and required the user to know the Sunday. Replaced with a stepper (`[← Prev] [Apr 26 – May 2] [Next →]` + `[Today]` + `<input type="date">` that snaps any picked day to the containing Sunday via `addDaysCairo(date, -dow)`). Every weekKey change is now a guaranteed-valid Sunday so `useEffect(fetchLog)` fires once per intentional action. Don't go back to free-text inputs for week-keys; if you need an arbitrary date input, snap it.
- **`matchesAutoRule` lives in `@/lib/permissions-constants.ts`, NOT `@/app/actions/permissions.ts`.** It's a pure synchronous predicate (no Redis, no FCM) used by both `createPermission` (the canonical decide path) and `simulateAutoRules` (the Sir-only `/admin/permissions` Simulate tab). It can't live in `permissions.ts` because that file is `'use server'` and can only export async functions. Don't move it back; don't duplicate it in admin.ts. The "extract pure predicates to a shared module" pattern is the right approach when the same logic needs to run from both a `'use server'` action file and another `'use server'` action file.
- **`/admin` landing has a four-chip dashboard strip at the top.** `<AdminDashboardStrip />` polls `getAdminLandingSummary()` every 30s and surfaces: pending permissions count, pending claims count, cron freshness (X/Y fresh), errors-last-24h. Each chip is a Link to the relevant deep page. Color tones: emerald for "0 / fresh," amber for "non-zero pending," rose for "stale crons / errors present." Don't fold this into a server action that runs on the landing's server-render — the polling is what makes it a live read; a one-shot server-render snapshot would be stale by the time Sir saw it.
- **`<RecentAdminActions />` shows the last 8 `[admin]`-prefixed entries from `activity:log` on the `/admin` landing.** Server action `getRecentAdminActions(limit)` filters `getActivity(500)` (cap-bounded, cheap) by message prefix. Hides itself when the result is empty so the landing doesn't show a stub. Drop the `[admin]` prefix when rendering — visual noise.
- **Score simulator on `/admin/rewards` Status tab is pure client compute.** No Redis writes. Reads the snapshot's `rawScore + multiplier + tiers + streakThreshold` and lets Sir nudge per-event-type counts up/down + add a manual signed-points adjustment. Recomputes `displayedScore = round(newRaw × multiplier)` and resolves the new tier locally via `[...tiers].reverse().find(t => displayed >= t.threshold)`. Highlights tier crossings + streak-threshold crossings. `manual_adjust` is excluded from the per-type rows because its weight is always 0 in storage and meaningless in the simulator; the dedicated "Manual adjust (signed pts)" input handles ad-hoc points.
- **Auto-rule simulator on `/admin/permissions` Simulate tab calls `simulateAutoRules(args)`.** Server action runs the same first-match-wins iteration as `createPermission` (using the shared `matchesAutoRule` predicate from permissions-constants), reads the live auto-rules from Redis, returns the matched rule + its decision + reply/terms/denialReason. NO writes, NO FCM, NO obedience event. Don't propose a "fire this simulation as a real request" button — the `/permissions` page exists for that, and the simulator's value is precisely that it doesn't side-effect.
- **Bulk trash operations loop the existing per-item actions.** `/admin/trash` multi-select bulk-restore and bulk-purge call `restoreTrashEntryAction` / `deleteTrashEntryAction` per row in sequence. NOT pipelined into a single Redis op — the per-item actions handle index ZSET removal, count adjustments, and revalidation; reproducing that in a bulk pipeline would duplicate logic with drift risk. At 200 max trash entries the sequential cost is fine. Selection state clears when the feature filter changes (selected items might no longer be visible).
- **Test push presets on `/admin/push-test` write directly to the form via DOM lookups, not state.** The form already lives inside `useActionState`; preset application is a DOM-level "fill the inputs" action via `formRef.current.querySelector('input[name="title"]')` etc. This avoids re-architecting the form to be controlled. Don't try to convert the form to controlled inputs just to enable presets — DOM-write is the smaller change.
- **`/admin/logs` Activity tab filters by level (chip group); Auth failures tab filters by IP (chip group of unique IPs from the loaded slice).** Filtering is purely client-side over already-loaded records (no refetch on filter change). The IP chip set is computed via `Array.from(new Set(records.map(r => r.ip).filter(...)))` so it's bounded by the loaded record count. Don't add server-side level filtering to `getActivityFeed` — the cap is 500, client-side filter is sub-ms.
- **Time integrity Diag block on `/admin/health` Health tab is pure client compute.** No server reads. Compares `tzOffsetMinutes(Cairo, now)` against expected UTC+2 (winter) or UTC+3 (summer) based on UTC month — if mismatch, flags it. Also sanity-checks `(now - cairoMidnightMs(today))` is in `[0, 24)` hours and `(tomorrowMidnight - todayMidnight)` is in `[23, 25]` hours (DST transition tolerance). The Egypt DST window is approximated as April–October; tighter alignment to "last Friday of April → last Thursday of October" wasn't worth the math at this scale. If the runtime ICU table ever drifts or DST policy changes, the offset Diag flips red.
