## Why This File Exists

Training data for current LLMs predates several intentional removals from this codebase. Common autocompletion failures:

- Importing `web-push` because the agent saw a notification helper and pattern-matched on Web Push tutorials.
- Writing `import { Serwist } from '@serwist/next'` because the agent inferred PWA support from the Capacitor presence.
- Referencing `process.env.VAPID_PUBLIC_KEY` because the agent assumed Web Push must be configured.
- Reading from `pages/api/...` because the agent's training cutoff predates App Router maturity.
- Re-suggesting voice notes for `/permissions` because audio attachments seem like a natural fit for emotional context. They were prototyped and removed — don't re-propose without explicit user instruction.
- Proposing a Telegram bot / Telegram fallback push / any third-party messenger as a notification channel because Honor / EMUI / no-GMS devices throttle FCM. The FCM defensive design (§ 3.3) — registration tolerance + the durable `notifications:{author}` history LIST + per-token failure pruning — is the sanctioned answer. Out-of-band messenger channels are explicitly banned; do not re-propose under any framing including "fallback," "sidecar," "parallel send," or "reliability hardening."

Every entry above produces a runtime failure, a bundle that won't compile, or a refused PR. Stop the moment you find yourself typing one.

## Easy mistakes that aren't on the removed list

These are not removed — they exist and are wired up. Listed because their existence is non-obvious and an agent might assume the wrong thing:

- **`@capacitor/geolocation`** is in use, not dormant. `DistanceCard` consumes it for live distance to `PARTNER_COORDS`. The `ACCESS_COARSE_LOCATION` / `ACCESS_FINE_LOCATION` perms in `AndroidManifest.xml` are real, not stale.
- **`@capacitor/device`** is in use for Sentry device context inside `SentryUserProvider`. Don't propose adding device-info plugins; one already runs.
- **`@capacitor/screen-orientation`** IS still installed but currently unused — flagging here so an agent doesn't mistake it for a future-use plugin already wired up. Either propose a real use or removal.
- **`/admin`** is a real Sir-only sub-tree (not a stub). Active routes: `/admin`, `/admin/trash`, `/admin/export`, `/admin/devices` (presence + FCM tokens + force-logout sessions + per-install records — old `/admin/inspector` lives as the "Right now" section, old `/admin/sessions` lives as the "Sessions" section), `/admin/health` (tabbed: Health / Cooldowns / Time — old `/admin/cooldowns`, `/admin/time`, `/admin/timezone` consolidated; Time tab hosts both the live snapshot and the Cairo↔Tabuk converter), `/admin/logs` (tabbed: Activity / Outbound / Restraint / Auth failures — old `/admin/activity`, `/admin/notifications`, `/admin/restraint-history`, `/admin/auth-log` consolidated), `/admin/push-test`, `/admin/rewards`, `/admin/permissions`, `/admin/redis`, `/admin/stats`, `/admin/mood`, `/admin/dates`. Layout guard at `src/app/admin/layout.tsx` redirects non-Sir; every action in `src/app/actions/admin.ts` repeats the role check via `requireSir()`. Don't add a route at `/admin/inspector`, `/admin/sessions`, `/admin/cooldowns`, `/admin/time`, `/admin/timezone`, `/admin/activity`, `/admin/notifications`, `/admin/restraint-history`, or `/admin/auth-log` — those were intentionally consolidated.
- **`moveToTrash` / `moveManyToTrash`** are real and wired into every `delete*` / `purgeAll*` action. Don't propose "adding a trash window" as future work — it exists. Don't bypass via a raw `del` either.
- **`session:epoch:{author}`** is the live force-logout mechanism. `decrypt()` reads it on every JWT verify (5s in-process cache). Don't reinvent revocation via deny-lists or jti-tracking.
- **`activity:log`** is the Sir-only feed. Driven automatically from `logger.interaction` / `warn` / `error` / `fatal` via `recordActivity` in `src/lib/activity.ts`. Don't call `recordActivity` directly from feature code.
- **`directive:{id}` + `directives:index` + `directive:active:Besho` are real** — the real-time directive overlay. `<DirectiveDialog>` mounts in root layout and self-gates on Besho. Single-slot via the active sentinel; reissue while active refuses. Cron-only expiration via `/api/cron/timer-expire`. Don't conflate with `directive_completed` / `directive_missed` obedience event types — those are scoring side-effects, not the storage layer. Don't call `expireDirective` from feature code; it's a cron-only mutator, same rule as `finalizeWeek`.
- **`punishment:{id}` + `punishments:index` + `punishment:active:Besho` are real** — the punishment timer. `<PunishmentOverlay>` mounts in root layout BEFORE `<DirectiveDialog>` (precedence). Single-slot. Cron-only timeout sweep via `/api/cron/timer-expire`. The auto-created `ledger:{id}` entry on completion / bail is written **inline** in `punishment.ts`, not via `createLedgerEntry` — going through the helper would emit the standard `ledger_punishment` and double-count against the typed `punishment_completed` / `punishment_bailed` events. Don't propose refactoring this to share with `createLedgerEntry`; the inline write is intentional. The `ledger.LedgerEntry.linkedPunishmentId` field is a back-reference, not a foreign-key constraint — soft-deleting a ledger entry does NOT cascade to the punishment record.
- **`PunishmentOverlay` uses channel `default`, NOT `safeword`.** The safeword channel is reserved for Besho→Sir distress + summon. Don't propose routing the punishment timer through it for "max priority" — `bypassPresence: true` + `priority: "high"` on the default channel is the right shape.
- **The directive ↔ punishment precedence is enforced by `<DirectiveDialog>` self-suppression**, not z-index. The dialog reads `getActivePunishment` alongside `getActiveDirective` and renders null when both are present. `<PunishmentOverlay>` dispatches `ourspace:punishment-cleared` on terminal transitions so the dialog refetches. Don't propose stacking via z-index — the modals are intentionally exclusive.
- **The `extraData` parameter on `sendNotification` is real** (added with the directive overlay). Merges into both foreground (`data`-only) and background (`notification` + `data`) FCM payloads. Values must be strings — FCM rejects nested objects. Used to pipe `kind` + feature-specific ids (e.g. `directiveId`) so the foreground listener in `<FCMProvider>` can route to the right surface. Don't pass non-string values; don't propose adding a `notification` field — the foreground/background split is what prevents Android double-banners.
- **`summonKitten()`** is real and lives in `src/app/actions/admin.ts`. It is the only Sir → Besho push that bypasses presence and uses the safeword channel. Surfaced via `<SummonButton>` on the `/admin` landing. Don't propose adding a cooldown, history list, or configurable copy without explicit instruction — those were all considered and rejected.
- **`<DeviceTracker />`** is mounted once in the root layout and owns every `device:*` write. `pingDevice` is the only writer. Don't propose calling `pingDevice` from feature code, adding presence-style polling, or merging it into `usePresence` — they're orthogonal: presence is per-author, devices are per-install. Web devices intentionally have no location (no permission prompt).
- **`assertWriteAllowed(author)`** in `src/lib/restraint.ts` is real and gates every Besho-writable server action. There is no middleware — the per-action guard is the model. Don't propose centralizing it into a wrapper or skipping it on "low-risk" actions; the wholepoint is uniform application.
- **`auth:failures`** is the failed-login ZSET. Written by `login()` only. Don't reuse it for unrelated security events; don't store the passcode value (only its length). The export tool dumps every key — keeping the value out is a privacy boundary.
- **`/api/cron/ritual-windows`** is one of five cron endpoints (the others: `obedience-sweep`, `review-window-open`, `timer-expire`, `heartbeat-watch`) and the only place writing `ritual:fcm:sent:*`. Triggered exclusively by cron-job.org (minute cadence, configured out-of-band in the operator's account). Don't propose calling it from feature code, adding a `vercel.json` cron, or removing the `CRON_SECRET` bearer check.
- **`/api/cron/timer-expire`** is the combined timer expiration sweeper (minute cadence). Calls `expireDueDirectives` (walks `directives:index`, expires past-`expiresAt` records, emits `directive_missed`) AND `expireDuePunishments` (walks `punishments:index`, bails `running` records past `endsAt + BACKGROUND_GRACE_SEC`, auto-creates a "bailed" ledger entry, emits `punishment_bailed`). Page reads (`getActiveDirective`, `getDirectiveHistory`, `getActivePunishment`, `getPunishmentHistory`) MUST NOT mutate state — same rule as `getRewardsBundle` not finalizing weeks. The combined route exists so the cron count stays bounded; don't propose splitting into separate `/api/cron/directive-expire` + `/api/cron/punishment-expire` endpoints.
- **Vercel tier is Hobby; there is intentionally NO `vercel.json` in the repo.** Hobby rejects build with any cron more frequent than once-per-day, and a daily-only fire was deemed not worth keeping. Adding a `vercel.json` with crons WILL break the next deploy. Cron-job.org is the sole trigger source.
- **`filter: blur()` was deliberately stripped from page transitions, the CounterCard, the Quote card, the BiometricGate exit, and the note-reactions list.** It tanks framerate on Android WebView (S21 Ultra etc. — verified user complaint). `popLayout` was downgraded to `wait` in the same pass. Don't re-add either to hot-path animations. The lone surviving blur is in `src/app/login/page.tsx` (one-time first-paint).
- **`backdrop-blur-xl` and `shadow-2xl` were swept across the whole codebase down to `backdrop-blur-md` and `shadow-xl shadow-black/30` (or `/40` on the floating navbar).** This is intentional perf work, not a stylistic accident. Don't bump them back up "for the premium feel" — they were tested on the S21 Ultra and the heavier values were what was breaking framerate. Modals (push-toast, notification drawer, permission dialog) that appear briefly and aren't animated over kept `shadow-2xl shadow-black/60`.
- **`will-change-transform` is applied only to**: `src/app/template.tsx` page-transition motion.div, the two `layoutId="navbar-active-indicator"` pills in the floating navbar, the CounterCard hero/anniversary AnimatePresence spans, and the More-sheet drawer in the floating navbar. Don't add it elsewhere without a measured perf reason — it eats GPU memory and overuse degrades performance.
- **The More-sheet drawer in the floating navbar runs WITHOUT `backdrop-filter`.** Earlier version had `backdrop-blur-md` on the drawer + `backdrop-blur-xs` on the overlay; that combination tanked open/close framerate on Android WebView (verified S21 Ultra). The drawer is now `bg-neutral-950` (fully opaque, no readback needed) and the overlay is plain `bg-black/60` (no blur). The visual difference is negligible because the overlay's opacity already darkens the page; don't re-add backdrop-filter without measuring on hardware.
- **`/rewards` is a real top-level route, separate from `/ledger`.** `/ledger` stays as Sir's manual log. `/rewards` is the automatic-tier surface driven by an obedience score. They're orthogonal — don't conflate. Tier count is fixed at 5. The score lives in `obedience:events:{author}:{weekKey}` ZSETs; the tier catalog in `rewards:tiers`; claims in `reward:claim:{id}`. Sir-only editor at `/admin/rewards`. Don't propose a parallel score system.
- **`recordObedienceEvent` from `src/lib/obedience.ts` is the only sanctioned emit.** Wired into `tasks.approveTask`, `rules.acknowledgeRule`, `rituals.submitOccurrence`, `permissions.createPermission` + `decidePermission`, `mood.submitMood`, `admin.setRestraintState`. The daily cron `/api/cron/obedience-sweep` owns the negative missed-event emissions (`task_missed`, `ritual_missed`, `rule_unacked`) — don't duplicate that logic in feature code. Member-key `{eventType}:{eventId}` makes retries idempotent.
- **State submissions are NOT scored.** Only `mood.submitMood` emits `mood_checkin` (+1 daily). `mood.submitState` is intentionally a free expressive surface — don't add a `state_checkin` event. The user explicitly removed that path.
- **Reward claims are append-only audit history.** No `deleteClaim` exists. Don't add one. Soft-delete is for first-class records (notes/rules/tasks/ledger/etc.), not for claim audit.
- **`/api/cron/obedience-sweep` is the second cron endpoint.** Same bearer-auth shape as `/api/cron/ritual-windows`. Triggered by cron-job.org once per day. Don't propose merging the two — different cadences (minute vs daily), different jobs.
- **`/api/cron/review-window-open` is the third cron endpoint.** Daily; the endpoint internally short-circuits on non-Saturdays. Dedup via `review:fcm:opener:{weekDate}` (25h TTL). Don't fire the opener from anywhere else (page actions, hooks, or other crons) — the dedup key only protects against repeat firings within the same Saturday.
- **Finalization is cron-only.** `getRewardsBundle` must NEVER call `finalizeWeek` or `catchUpFinalizations`. Page reads that finalize fire FCMs as a side-effect; the previous lazy-on-read pattern produced 4×2=8 notification spam on `/rewards` visits after a fresh deploy. `catchUpFinalizations` is exported solely for `/api/cron/obedience-sweep` to call. If you find yourself wanting to finalize from a page or feature action, you're in a bug.
- **`finalizeWeek` uses `SET NX` for atomic lock acquisition.** The previous `if (await isWeekFinalized(...)) return` followed by ~5 awaits and a pipelined `SET finalized "1"` had a multi-second race window — two concurrent invocations (cron-job.org retrying within seconds, OR Sir clicking `recomputeWeek` while the cron was running) could both pass the guard and both fire the recap FCM. Observed in production as duplicate "📊 Week wrapped" notifications on 2026-05-08. The fix replaces the read-then-write split with an atomic `redis.set(finalizedKey, ts, { nx: true })`: the first caller wins the lock, the second sees the sentinel exists and bails. The sentinel value carries the finalize timestamp instead of `"1"` so debugging can answer "when did this week finalize" without trawling the activity log; `isWeekFinalized` checks truthiness (NOT `=== "1"`) so any non-empty string/number is fine. On catastrophic failure inside the lock, the sentinel is `DEL`'d so retries can re-attempt — without that, an Upstash hiccup mid-pipeline would leave the week stuck "finalized" with no data updates.
- **The "📊 Week wrapped" recap FCM has its OWN dedup sentinel — `obedience:week-wrapped-fcm:{author}:{weekKey}`** — separate from `finalizedKey`. SET NX EX 60d, set inside `notifyWeekClosed` BEFORE the FCMs fire. This is the only thing that guarantees once-per-week-forever idempotency for the user-visible push: `finalizeWeek`'s lock can be released on error AND can theoretically be re-acquired by an admin `recomputeWeek` after a transient failure, AND the legacy `"1"` sentinel value was historically subject to Upstash auto-parse weirdness (`"1"` → `1`, breaking strict-equality checks). Mirrors the established pattern of `review:fcm:opener:{weekDate}`, `streak-risk:fcm:sent:*`, `reward:claim:nudge-sent:*`, `ritual:fcm:sent:*` — every cron-fired FCM has a dedicated dedup sentinel. **Observed in production (2026-05-08 → 2026-05-09) as a daily duplicate "Week wrapped — Apr 26 – May 2" recap** because the finalize-side dedup wasn't enough on its own. If Sir ever needs to force-re-fire the recap (rare, e.g., bug fix scenario), `DEL` the sentinel via `/admin/redis` and retrigger via the obedience-sweep cron or admin recompute.
- **Ritual reminders are FCM-only — no LocalNotifications scheduling.** The `/rituals` page used to schedule on-device LocalNotifications for upcoming windows in parallel with the cron-fired FCM, producing a double-buzz at every window-open. The scheduling effect is now a one-shot blanket-cancel on mount (clears the [3000, 3895] band of any stale device-side reminders). `/api/cron/ritual-windows` is the sole signal source. Don't propose re-adding device-side scheduling for rituals; the cron is reliable and runs even when the app is closed.
- **`ledger_punishment` is a real `ObedienceEventType`.** Fires automatically from `ledger.createLedgerEntry` when `type === "punishment"`; reward entries do NOT emit. Default weight −10, tunable in `/admin/rewards` weights tab. Don't propose a parallel ledger-rewards-grant-points pathway — `/ledger` rewards are intentionally a Sir manual log only; the score-driven path is `/rewards`.
- **Per-event deletion exists.** `adminDeleteObedienceEvent` (Sir-only) removes a single emit from both the events ZSET and the audit ZSET. Score recomputes naturally on next read. Don't add a "negate" or "compensate" inverse-emit pathway — the canonical fix for a wrong event is delete + (optional) `manual_adjust` to add anything new. Per-event deletion is surfaced in `/admin/rewards` Status tab → Event log as a per-row trash button (two-tap confirm).
- **Tier emojis are real.** `RewardTier.emoji` is optional (≤8 chars). Snapshotted onto `RewardClaim.tierEmoji` at claim time. Default seeds use 🥉 🥈 🥇 🏆 👑 — Sir can override per-tier in `/admin/rewards` Tiers tab.
- **Test mode is a single Sir-controlled flag** (`obedience:test-mode`). When ON, `claimReward` accepts the current week without finalizing it. Don't add per-author or per-author-and-week granularity; this is a global diagnostic flag for verifying the claim → deliver flow. The week itself stays unfinalized — streak counter and frozen multiplier are NOT touched. UI: `/admin/rewards` Status tab toggle; `/rewards` shows a `TestModeBanner` and `CurrentWeekClaimSection` when on.

- **Test push presets on `/admin/push-test` write directly to the form via DOM lookups, not state.** The form already lives inside `useActionState`; preset application is a DOM-level "fill the inputs" action via `formRef.current.querySelector('input[name="title"]')` etc. This avoids re-architecting the form to be controlled. Don't try to convert the form to controlled inputs just to enable presets — DOM-write is the smaller change. The recipient field is a 3-way radio (`T7SEN` / `Besho` / `Both`) — picking `Both` makes `sendTestPushAction` fan out to both authors via `Promise.allSettled`, returning a partial-success error string when only some delivered. The 12 presets bias toward Sir (8 of 12 — perm-request, reward-claim, reward-received, task-submitted, ritual-submitted, stale-claim, auto-decided, rule-ack) because that's whose end-to-end push surface most needs verifying; 3 to `Both` (review-window, week-wrapped, smoke-test) cover broadcast events; 1 to kitten (tier-unlock).
- **`/admin/logs` Activity tab filters by level (chip group); Auth failures tab filters by IP (chip group of unique IPs from the loaded slice).** Filtering is purely client-side over already-loaded records (no refetch on filter change). The IP chip set is computed via `Array.from(new Set(records.map(r => r.ip).filter(...)))` so it's bounded by the loaded record count. Don't add server-side level filtering to `getActivityFeed` — the cap is 500, client-side filter is sub-ms.
- **Time integrity Diag block on `/admin/health` Health tab is pure client compute.** No server reads. Compares `tzOffsetMinutes(Cairo, now)` against expected UTC+2 (winter) or UTC+3 (summer) based on UTC month — if mismatch, flags it. Also sanity-checks `(now - cairoMidnightMs(today))` is in `[0, 24)` hours and `(tomorrowMidnight - todayMidnight)` is in `[23, 25]` hours (DST transition tolerance). The Egypt DST window is approximated as April–October; tighter alignment to "last Friday of April → last Thursday of October" wasn't worth the math at this scale. If the runtime ICU table ever drifts or DST policy changes, the offset Diag flips red.
- **`togglePinNote` uses a per-author SETNX lock to serialize the count-then-write critical section.** Upstash REST has no WATCH/MULTI, so two simultaneous toggles can each observe count=4 and both write — landing at 5 over `MAX_PINS_PER_AUTHOR`. Lock key is `notes:pin-lock:{author}` with 5s TTL (auto-clears if request crashes mid-flight). On contention the second caller returns `{ error: "Another pin operation is in progress. Try again." }`. The race is exceedingly rare in a 2-user app, but the user-visible "retry" message is preferable to silently exceeding the cap. Don't refactor to a per-author counter without also wiring decrements into `deleteNote` + `purgeAllNotes` + the toggle's unpin path; the lock is the smaller correct change.
- **The dashboard route IS `/`, NOT `/dashboard`.** `src/app/page.tsx` is the dashboard; there is no `/dashboard` route — tapping a push with `url: "/dashboard"` lands on the 404. `usePresence("/", ...)` is what the dashboard registers, and `safeword.ts` / `summonKitten` / `sendHug` all use `url: "/"` to match. Don't reintroduce the `/dashboard` literal anywhere; the writer-vs-reader symmetry is what makes the "skip if on target page" check in `sendNotification` work for non-bypass pushes.
- **Both `default` AND `safeword` Android notification channels are registered in `<FCMProvider>`.** Only registering `default` and then setting `android.notification.channelId: "safeword"` on outbound FCMs silently falls back to `default`, neutering the max-priority + sound semantics that safeword + summon depend on. The `safeword` channel is `importance: 5, visibility: 1, sound: "default", vibration: true`. Channels are created on-device per install — first effect lands on next APK open after the FCMProvider runs. Don't strip the second `createChannel` call thinking it's redundant; it's the difference between heads-up emergency alerts and silent ones.
- **Web Push (browser VAPID) is REMOVED — no route, no consumer, no key.** `/api/push/subscribe` does not exist; `<NotificationButton>` does not exist; `push:subscription:{author}` is never written. The only push path is FCM via `/api/push/subscribe-fcm` (token registration in `<FCMProvider>`). The UI in `src/app/tasks/page.tsx` only renders the Submit button under `isBesho`, but the server check is the actual boundary. An earlier per-page touch-handler implementation (handleTouchStart/Move/End + indicator JSX) raced the global handlers, double-firing on the same gesture. Don't reintroduce per-page touch handlers on `/permissions` (or any other page) — the global PTR is the single source.
- **All primary form submits are offline-gated via `useNetwork`.** Pattern: `const { connected } = useNetwork(); const isOffline = !connected;` then `<Button disabled={isPending || isOffline || undefined}>`. Applied across `/notes`, `/tasks`, `/rules`, `/timeline`, `/ledger`, `/rituals` (both forms), `/protocol`, `/permissions` (both forms — RequestForm + QuotaModal), `/review` (folded into `canSubmit`). Don't ship a new primary-submit form without the offline gate; AGENTS.md § Coding Pattern 18 enforces this. Sub-component forms call `useNetwork` themselves — don't drill `isOffline` as a prop.
- **`<SessionGuard>` mounted in root layout polls `getCurrentAuthor()` every 60s.** Catches mid-session expiry — e.g. when Sir force-logouts the other author via `forceLogoutAuthor()` (bumps `session:epoch:{author}`), or when a 30-day JWT expires while the app is open. On transition `string → null` it `router.replace("/login?expired=1")`; `/login` reads the param and surfaces a "Your session ended" banner. Initial null is NOT a trigger (BiometricGate may still be resolving on cold start). Don't add per-page session checks — the guard is the single source. Don't increase the poll cadence: 60s is the bound on how stale the redirect can be, and bumping it down trades cache hits for marginal UX gain. The component is sibling to `<BiometricGate>`'s children, mounted once.
- **Tasks / rituals / permissions error banners mirror `/notes`'s `pinError` pattern.** `useState<string | null>` for `actionError`, transient banner JSX with `role="alert"` and `<AnimatePresence>` exit, auto-clear via `setTimeout(() => setActionError(null), 3000)` in a useEffect keyed on the error. Plumbed into:
  - `/tasks`: `handleSubmit` / `handleApprove` / `handleReject` / `handleDelete` (all four action handlers, not just delete — they shared the same silent-no-op shape and the marginal cost of plumbing each was one line)
  - `/rituals`: `handleDelete` only (other write paths route through sub-components or `useActionState` with their own error handling)
  - `/permissions`: `handleDeleteRequest` (the snapshot rollback was already there; the banner surfaces the WHY to the user)
  When adding new mutating action handlers in any of these three pages, plumb to the existing `setActionError` — don't introduce a parallel state.
- **Notes search auto-loads remaining pages on `onFocus`.** The substring filter is in-memory, so without all pages loaded a search can return "0 results" while older matching notes sit in pagination. `loadAllRemaining()` is the shared helper — used by both `handleFilterChange` (when switching to a non-`all` filter) and `handleSearchFocus` (search input's `onFocus`). Re-entrancy guarded by `isLoadingMore`. The result hint shows "(loading more…)" while the drain is in flight; the older "(in loaded notes)" copy was removed because after focus the corpus IS the full corpus. Don't add server-side notes search — at 2-user scale the full client filter is sub-ms.
- **Rituals 30s poll is gated on tab visibility AND online status.** Background tabs and offline devices skip the fetch. Pattern: read `document.visibilityState === "hidden"` via the `globalThis as unknown as { document?: ... }` cast, plus `connected` from `useNetwork()`. Don't remove these gates "for simplicity" — they're the difference between burning Upstash REST calls every 30s when the user has the app backgrounded vs only firing when the user is actually looking. Other pages' polls (devices admin, dashboard strip) should follow this same pattern.
- **Refresh-button spinners use `aria-busy` + dynamic `aria-label`.** Pattern: `aria-busy={isRefreshing || undefined}` + `aria-label={isRefreshing ? "Refreshing X" : "Refresh X"}`. Visual `animate-spin` alone is invisible to assistive tech. Applied on `/notes` and `/rewards`; carry the pattern when adding refresh buttons elsewhere.
- **`src/app/actions/admin.ts` is split: orchestration core (~1.6k lines) + 5 bucket modules under `src/app/actions/admin/`.** The split surfaces are:
  - `admin/permissions.ts` — auto-rules JSON, quotas, bulk-decide, simulator
  - `admin/rewards.ts` — tiers, weights, streak, snapshot, recompute, manual adjust, event log, test mode, claim purge, per-event delete
  - `admin/health.ts` — cooldowns, health snapshot, repair indexes, cron telemetry, drift repair, bucket-shift migration, deploy info, redis inspector
  - `admin/notifications.ts` — summon, test push, outbound audit, resend
  - `admin/devices.ts` — inspector, sessions, devices, restraint state + history
  - `admin/_shared.ts` — non-`'use server'` module exporting the Upstash `redis` client singleton, `PRESENCE_FRESH_MS`, `getSession()`, `requireSir()`. Has `import "server-only"` so it never ships client-side. Bucket files AND admin.ts itself import helpers from here — there is exactly ONE `new Redis(...)` instantiation across the whole admin surface (in `_shared.ts`).
  All external callers continue to import from `@/app/actions/admin` — admin.ts re-exports every bucket symbol. Don't add new admin actions to the slimmed admin.ts; pick the right bucket. The orchestration core retains: activity feed, JSON export, auth-failures, dates, mood/state overrides, stats + heatmap, trash, landing summary widgets.
- **Re-exporting server actions across `'use server'` files uses one-line wrapper functions, NOT `export { foo } from "./bar"`.** Turbopack rejects `export { ... } from` and `export * from` in `'use server'` files at the syntactic check ("Only async functions are allowed to be exported"); `tsc` accepts them but the build fails. The pattern in admin.ts is:
  ```ts
  import { foo as _foo } from "./admin/bucket";
  export async function foo(...args: Parameters<typeof _foo>): ReturnType<typeof _foo> {
    return _foo(...args);
  }
  ```
  Type re-exports work cleanly via `export type { ... } from "./admin/bucket"` because interfaces erase at compile time. Don't try to "simplify" the wrappers to direct `export { foo } from` — the build will fail. The wrapper hop is microseconds of overhead, fine for admin actions.
- **`PERMISSIONS_INDEX` and `permissionRecordKey` are duplicated as private consts in admin.ts and admin/permissions.ts.** Both bucket and orchestration core need them (`getAdminLandingSummary` in admin.ts inspects the permissions index for the dashboard strip's pending count). The values are identical (`"permissions:index"` and ``id => `permission:${id}` ``); duplicating avoids a cross-bucket import that would couple the orchestration core to the permissions bucket. Don't extract these into _shared.ts unless you also pull in the rest of the permissions feature primitives (key shapes, etc.) — the cleaner path is the one currently shipped.
- **`SessionGuard` mounted in root layout polls `getCurrentAuthor()` every 60s.** Catches mid-session expiry — e.g. when Sir force-logouts the other author via `forceLogoutAuthor()` (bumps `session:epoch:{author}`), or when a 30-day JWT expires while the app is open. On transition `string → null` it `router.replace("/login?expired=1")`; `/login` reads the param and surfaces a "Your session ended" banner.
  (Note: this entry was added earlier alongside the SessionGuard component itself — kept here intentionally because the admin.ts split moved `forceLogoutAuthor` into `admin/devices.ts`. The `@/app/actions/admin` re-export path still resolves it transparently.)
- **`/api/presence/beacon` was removed — the beacon path is gone.** `usePresence` previously called `navigator.sendBeacon("/api/presence/beacon", ...)` on tab hide, but the route never existed (silent 404). The fix is to call `clearPresence()` directly on hide/pagehide; the existing fetch DELETE uses `keepalive: true`, which is the modern equivalent of sendBeacon and works during page unload. Don't reintroduce the beacon call unless you also add the matching server route. Native Capacitor uses `App.addListener("appStateChange")` for the equivalent lifecycle.
- **Quote daily seed uses Cairo TZ via `todayKeyCairo()`, not server-local Date.** Earlier the seed was `year*10000 + month*100 + day` from `new Date()`, which on Vercel resolves to UTC. Cairo got the new daily quote 2-3h late. Fixed: parse `todayKeyCairo()` (`YYYY-MM-DD`) and reconstruct the same numeric shape. Don't go back to a Date-based seed; any user-facing daily-rotating data should bucket by Cairo day.
- **`getNavBadges` filters tasks by `status === "pending"`, NOT the legacy `!completed` boolean.** New tasks are status-driven (`pending`/`in_review`/`completed`); the legacy `completed?: boolean` lingers on the Task type but isn't authoritative. Without the migration the badge counted in-review tasks (kitten already submitted, awaiting Sir) as still-pending obligations on her side, which was wrong. The filter falls back to `completed ? "completed" : "pending"` for legacy records that never got a `status` field — same JIT migration shape as `getTasks()`. Don't drop the legacy fallback until you've confirmed every task record in Redis carries a `status`.
- **`getRewardsHistory` parallelizes its per-week loop.** A 12-week history was 12 sequential `await Promise.all([state, claim])` iterations (~24-36 RTTs); now it's one outer `Promise.all` over the full window (~2 RTTs). Don't refactor back to sequential — the lifted parallelism is the whole point.
- **`acknowledgeRule`, `submitTask`, `submitOccurrence` now `revalidatePath("/")`** in addition to their feature path. Nav badges (`useNavBadges`) and dashboard surfaces depend on the root route's RSC cache being fresh after these mutations. The badge polling hook re-fetches every 30s anyway, but `revalidatePath("/")` ensures the next navigation to `/` shows fresh state without waiting for the poll. Carry this pattern when adding new mutating actions that change badge-counted state.
- **`@/lib/redis` is the singleton Upstash REST client.** Exactly ONE `new Redis({...})` across the whole codebase, in `src/lib/redis.ts`. Has `import "server-only"` so client bundles can't reach it. Every server action, cron route, lib module, and admin bucket file imports `redis` from here. Pre-singleton, ~28 modules each instantiated their own client; cold starts built 28 connection pools before the first request. Don't add a second instantiation; if you find a module that needs Redis, import `redis` from `@/lib/redis`.
- **`src/lib/activity.ts` is the lone exception to the Redis singleton — keeps its own lazy null-safe client.** Why: `activity.ts` is statically imported by `logger.ts`, which is statically imported by client components (`error-boundary.tsx`, `error.tsx`, dashboard pages). If `activity.ts` imported the server-only `@/lib/redis`, the build would fail with a `[Client Component SSR]` chain. Even a dynamic import in `logger` (`await import("./activity")`) doesn't help — Turbopack tracks dynamic imports for chunk graphs and the `import "server-only"` pragma fires regardless of static/dynamic. The lazy null-safe pattern in `activity.ts` (`getRedis()` returns null when env vars are undefined) handles client-side bundle inclusion gracefully — `recordActivity` no-ops when env is missing. Don't try to "fix" activity.ts to use the singleton; the failure mode is well-understood and the second client is an acceptable cost.
- **Next 16 renamed Middleware → Proxy.** The file is `src/proxy.ts` (NOT `src/middleware.ts`); the named export is `proxy` (not `middleware`). Same lifecycle, same `next/server` request/response API. The build manifest shows it as `ƒ Proxy (Middleware)` for back-compat clarity. Don't create a `middleware.ts` — Next 16 will recognize the file but the team has standardized on Proxy terminology going forward. Same matcher syntax via `export const config = { matcher: [...] }`.
- **`src/proxy.ts` does three things, in order**: (1) global auth gate — unauthenticated visitors bounce to `/login` from any non-login page; (2) Sir-only gate on `/admin/*` — authenticated-but-not-Sir bounce to `/` (NOT `/login`, since they already authenticated); (3) session refresh — re-issues a 30-day JWT when there's <7 days remaining. All `/admin/*` responses get `Cache-Control: no-store, private` to prevent any CDN/browser caching. The admin layout's `requireSir()` redirect remains as defense-in-depth — proxy is the first boundary, layout the second. Don't remove the layout's redirect under the assumption the proxy is sufficient.
- **`heartbeat-watch` is the fourth cron + the meta-watcher.** Added to `CRON_NAMES` in `src/lib/cron-telemetry.ts` alongside `obedience-sweep`, `ritual-windows`, `review-window-open`. Reads telemetry for the OTHER three crons, compares each `lastRun.ts` against an expected fresh window (30h for daily crons, 10m for the minute cadence), and fires `sendNotification("T7SEN", ...)` when any are stale. Sentinel-deduped via `cron:stale-notified:{name}` (24h TTL) so a single stuck cron doesn't generate 48 alerts/day if heartbeat-watch runs every 30 minutes. Skips itself in the staleness check (no self-monitoring); Sir reads `/admin/health` to confirm heartbeat-watch is alive. **Add the URL to cron-job.org separately, every 30 minutes.** Without that step, the route exists but never fires.
- **Sentry server + edge configs filter the same noise families as the client config.** `sentry.server.config.ts` and `sentry.edge.config.ts` each have an `ignoreErrors` array matching `AbortError`, `UND_ERR_SOCKET`, `Connection terminated`, `fetch failed`, `socket hang up`, `ECONNRESET`, `Failed to fetch`. The Edge SSE route (`/api/notes/stream`) routinely surfaces `AbortError` when WebView pauses or user navigates away mid-stream — that's expected, not actionable. Server-side `fetch failed` is undici (Node fetch) talking to Upstash REST or Firebase HTTP v1 over flaky TLS. Don't surface these to Sentry.
- **Reactions log at `info` level, NOT `interaction`.** Reaction toggles are high-frequency (every emoji tap) low-signal events. Logging at `interaction` writes to `activity:log` (capped at 500), which evicts higher-signal `[admin]`/`[auth]` events under load. `logger.info` is excluded from `recordActivity`'s level filter so reaction taps stay in console + Sentry breadcrumbs but don't crowd the activity feed. Don't upgrade reactions back to `interaction` without addressing the cap.
- **`/admin/devices` poll cadence is 15s with visibility gate.** Was 5s; reduced 3× to cut Upstash REST cost and Sir's phone battery drain. The `setInterval` checks `document.visibilityState === "hidden"` and skips the fetch when the tab is backgrounded; the relative-time tick (1s) keeps running so labels update when the tab returns to focus. Same visibility gate added to `/admin/health` 1s tick. Apply the same pattern to any new admin polls.
- **Capacitor `appendUserAgent: "OurSpaceAPK"` distinguishes APK from web in Sentry's `browser` tag.** Pre-fix, Sir-only desktop browser sessions and APK sessions all reported the same generic Chrome UA — making it hard to tell which surface a Sentry issue came from. Now: APK sessions append `OurSpaceAPK` to their user agent. Also: `server.allowNavigation: ["t7senlovesbesho.me"]` makes the in-WebView navigation boundary explicit; any link to a non-app host opens in the system browser. The dead iOS-only `PushNotifications.presentationOptions` config block was removed — this is an Android-only app.
- **Removed devDependencies: `concurrently`, `esbuild`, `tailwindcss-animate`.** Verified zero imports/script-references before removing. Note specifically: the active animate package is `tw-animate-css` (imported via `globals.css`), NOT `tailwindcss-animate` — those are different libraries with similar names. Don't reintroduce any of the three without a concrete consumer.
- **`markAllNotificationsRead` uses an EVAL Lua script for atomicity.** Pre-fix: read snapshot via LRANGE → DEL → re-push the snapshot via pipeline. A concurrent `pushNotificationToHistory` LPUSH between the LRANGE and DEL would be lost — DEL clears the new entry, re-push only writes the stale snapshot. Inside an EVAL the entire script runs uninterrupted (Redis is single-threaded), so concurrent LPUSHes wait for completion and aren't dropped. The script does an in-place string substitution `"read":false` → `"read":true`, relying on Upstash's canonical `JSON.stringify` form (no whitespace) for the byte-exact pattern. Don't change the JSON encoding shape elsewhere without updating the gsub pattern.
- **`HealthSnapshot.cron.secretSet` is a build-time env probe.** `getHealthSnapshot` checks `process.env.CRON_SECRET` and exposes a boolean; `/admin/health` renders it as a Diag row. The Diag row is the early-warning signal. Don't remove it; don't extend it to expose the secret value (only the boolean).

Ledger entries are anchored to the relationship's home zone; the input default should match. - **Timeline emoji picker is a `role="radiogroup"` with `role="radio"` buttons.** Roving tabindex (`tabIndex={isSelected ? 0 : -1}`), `aria-checked`, `aria-label`, and an `onKeyDown` handler that maps Arrow / Home / End to selection changes. - **`purgeAllRituals` parallelizes the per-ritual ZRANGE.** Was a sequential `for await` loop — one round-trip per ritual to fetch its occurrence index. Now: `Promise.all` over all rituals, single Upstash REST wave. Same fan-out shape used in `getRewardsHistory`. When fanning out per-record fetches in admin/destructive paths, default to `Promise.all`; sequential await is only correct when each iteration depends on the previous result.
- **`react-hooks/purity` flags `Date.now()` and `new Date()` at render time** (including inside `useMemo` factories — they re-run on render). The escape hatch is `useState`'s lazy initializer: `const [now] = useState(() => Date.now())` runs ONCE at mount and the lint rule treats that as out-of-render. Pattern for "now-ish" values: `const [mountedAt] = useState(() => Date.now()); const now = snapshot?.generatedAt ?? mountedAt;` — server-provided timestamps take precedence when available, the mount baseline fills the loading window. Don't compute `Date.now()` inside `useMemo` to satisfy a stale-cache instinct; the rule doesn't accept it.
- **One-shot client migrations are gated by `@capacitor/preferences` flags, NOT in-memory refs.** The ritual reminder-band cleanup (clears stale `[3000, 3895]` LocalNotification IDs from previous app versions) used to gate on a `firstReconcileRef.current` ref — that suppressed re-runs within a single page load but every cold start re-ran the full cancel band.
